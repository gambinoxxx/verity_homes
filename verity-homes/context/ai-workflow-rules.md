# AI Workflow Rules

## Approach

Build this project incrementally using a spec-driven workflow:

- **What to build:** `context/project-overview.md`, with the visuals in
  `design/`.
- **How to build it:** `context/architecture.md`,
  `context/code-standards.md` and `context/ui-context.md`.
- **Where we are:** `context/progress-tracker.md`.
- **How to prove it works:** `testing/TESTING.md`.

Always implement against these specs. Don't infer or invent behaviour.

## Session start (every time)

1. Read all files in `context/` and `testing/TESTING.md`.
2. Open `context/progress-tracker.md` and work only on the unit marked
   `in progress`. If none is marked, take the first `todo` unit and mark it
   `in progress`.
3. Open the `design/` file(s) that unit names and study them before
   writing code.

## Scoping rules

- Work on one unit at a time, and prefer small, verifiable increments.
- Don't combine unrelated system boundaries in one step.
- Split a step if it mixes:
  - public UI with admin UI
  - a schema change with the UI that uses it
  - more than one entity's CRUD
  - behaviour the context files don't define

If a change can't be verified end to end quickly, the scope is too broad,
so split it.

## Handling missing requirements

- Never invent business facts: phone numbers, addresses, prices, return
  rates, testimonials, partner names, statistics or CEO details. Use the
  visibly marked placeholders from `design/`, or seed rows with
  `[SAMPLE]` in the title.
- If something is ambiguous, write it under **Open questions** in
  `progress-tracker.md`, choose the most conservative option, and say so in
  your report.

## Protected files

Don't modify these unless the user explicitly says so:

- `design/**`: the reference designs
- `components/ui/**`: generated by the shadcn CLI. Regenerate them, don't
  edit.
- `prisma/migrations/**` once applied. Change `schema.prisma` and create a
  new migration instead.
- `lib/generated/**`: the generated Prisma client
- `.env*` files and secrets. Only `.env.example` may change.

## Keeping docs in sync

When implementation changes architecture, the schema, standards, tokens or
scope, update the matching `context/` file in the same unit.

## Definition of done (before marking a unit `done`)

1. `npm run lint`, `npm run typecheck` and `npm run test` all pass.
2. `npm run build` passes.
3. The unit's Playwright specs pass: `npm run test:e2e -- <spec>`.
4. You captured screenshots at 1440px and 390px and compared them with the
   matching `design/` file, then fixed visible differences in layout,
   spacing, colour, type or missing elements.
5. There are no console errors and no horizontal scroll at 360px.
6. No invariant in `architecture.md` was broken.
7. `progress-tracker.md` is updated: the status changes, a one-line note
   says what was built, and any open questions are added.
8. Your final message to the user lists:
   - what changed
   - the test results
   - the screenshot paths
   - anything the user must do by hand, such as env vars or Clerk dashboard
     settings
